New to AMUMSS? READ THIS 
    Read 'README\README-USAGE.txt' for general information using AMUMSS
    
    AMUMSS, at its most basic, process instructions in 'user scripts' written in the LUA 5.4 language
    
    Using those scripts is very simple:
       => You just put the scripts in the ModScript folder and double-click/execute BUILDMOD.bat
          Answer a few questions and mod will be created in CreatedMODS folder.
    
    More advanced usages are possible, you will learn them as you read information in this README
       under the section above called 'On this tab: USEFUL INFORMATION'
       and ask questions in >>> No Man's Sky Modding 'Invite' on Discord
          
    Learning to create new scripts takes time!
       But there exists a lot of scripts examples in 'TOOLS\ModLuaLearningCollection' folder 
       and real scripts in use, in >>> AMUMSS Script Collection on github
       specially those learning examples in >>> AMUMSS-ModLuaLearningCollection
       that can help one in learning how to write scripts.
    
    A good understanding of NMS files (mainly MXML files decompiled from MBIN files) will also help
    
    Again do not hesitate to ask questions in >>> No Man's Sky Modding 'Invite' on Discord

Which parts of the LUA language can I use in scripts? 
    All parts of LUA 5.4 The Language are available.
    
    Most parts of LUA 5.4 The Standard Librairies are available as listed here:  
        - All available standard libraries in {string, math, table}
        - io.open, io.input, io.type, io.read, io.lines and io.close
        - os.clock, os.date, os.difftime, os.getenv, os.time, os.tmpname
        - assert, coroutine, getmetatable, ipairs, next, pairs, pcall, print, select,
          setmetatable, tonumber, tostring, type, xpcall

    In addition, special functions listed here:
    - lfs.currentdir, lfs.attributes and lfs.dir from LuaFileSystem Reference
    
    - printf(s,...):
        A shortcut function to print formatted text 'print(string.format(s,...))'
    
    - WFAK([msg[,waitUntil]]):
        A shortcut function to Wait_for_any_key press from the user until 'waitUntil' sec.
        * msg: (optional) a string with your wait message or 'Press any key to continue . . .' if nil
        * waitUntil: (optional) a float value in seconds to wait for the key press before continuing
                     if nil then wait forever
    
    - NormalizePath(pathFilename[,IsStripExtension]):
        A function that normalize filepaths use in AMUMSS.
        * pathFilename: a string like: "METADATA/REALITY/CATALOGUECRAFTING.MBIN"
        * IsStripExtension: (optional) a boolean.  If true, the extension is stripped from the returned value
        
        NormalizePath(pathFilename) returns, in this case, the string value: "METADATA\REALITY\CATALOGUECRAFTING.MBIN"
        
        NormalizePath(pathFilename,true) returns, in this case, the string value: "METADATA\REALITY\CATALOGUECRAFTING"
          ==>> This last one is used as a key to internal tables in AMUMSS for modded MXMLs
    
    - GUIF({default_value as string|number|bool, prompt as short|long string}, OPTIONAL Wait):
      --> (GUIF means: Get_User_Input_Function)
        An internal function that can be used to request information from the script user while it is processed.
        >>> GUIF() (click for more info) can be used in a script body AND in VCT of MXML_CHANGE_TABLE 
        
        GUIF() will return a value of the same type() as 'default_value' is
            * no user input and just 'ENTER' key will return the default value
            * if the input is not of the type required, the default value is returned
            * 'bool' will return a boolean
                  will ask for Y/N like: Enter Y/N:
                  but User input can be any of (0/n/N/false/FALSE or 1/y/Y/true/TRUE)
                  if they wish (case does not matter)
            * 'number' will return a number
                  will ask for a number like: Enter Num:
            * 'string' will return a string
                  will ask for a string like: Enter Str:  
            * If 'Wait' parameter is used, after the delay in sec, 
                  GUIF will continue processing, using the default value
            * If 'Wait' parameter is nil or omitted, 
                  GUIF will wait indefinitely before continuing processing
    
    - GetLargeHex(number as string)
        * An internal function that can be used to get the string representation
          of a very large number passed as a string.
          >>> GetLargeHex(numberStr) can get, for example, a seed value.
              ==> GetLargeHex("18389095073394320520")) --> FF33308A268DE488
        
    - GNH(name as string) (meaning: Get_Name_Hash_Function)
        * An internal function that can be used to request the Jenkins HASH of a name.
          >>> GNH() can be used in a script body AND/OR in VCT of MXML_CHANGE_TABLE 
        * See also AUTO_GNH when using ADD to auto-generate NameHash values
        
        * GNH(name) will return the Jenkins HASH of the STRING / variable name
    
    - dofile([path]filename as string)
        * An internal AMUMSS function (not to be used inside NMS_MOD_DEFINITION_CONTAINER table)
          With the same functionality as the LUA Basic Function 'dofile(filename)' (except no stdin input) 
           - Opens the named file, executes its contents as a Lua chunk and returns all values returned by chunk.
        
        * 'filename' is always the name of a script to load
        * spaces are allowed in 'filename' and 'path'
        
        * Using "Test_DOFILE_GUIF.lua" of the AMUMSS TEST_SCRIPTS collection as an example:
          - You can find files required to run it in the 'TEST_SCRIPTS' folder
            *   TEST_HELPER_SCRIPTS_local as a local folder of 'TEST_SCRIPTS'
            *   and other files to use are in the 'Files to use with Test_DOFILE' folder
            *   Test_DOFILE_GUIF.lua (the test script)
                and, if you want to run it, replicate the 'normal folder structure' shown at the top of the script
            
        * '[path]filename' (see examples below)
          - can simply be the 'filename' of the helper LUA script (no path)
               >>> In this case, the helper script is found in ModScript\ModHelperScripts folder
                   ex.: dofile([[SayHello_1.lua]])
                   
          - can be a 'relative path + filename' 
               >>> relative to the current script folder or sub-folder
                   (here a sub-folder of "TEST_SCRIPTS" folder)
                   ex.: dofile([[.\TEST_HELPER_SCRIPTS_local\SayHello - child_2_local.lua]])
                   
               >>> if not found, a 'relative path + filename' to ModScript\ModHelperScripts folder
                   ex.: dofile([[..\..\TEST_HELPER_SCRIPTS_MAIN\SayHello - child_3.lua]])
            
          - can be a 'FULL path + filename' 
                   ex.: dofile([[C:\Test dofile\SayHello - child_5.lua]])
          
          - can be a 'path relative to AMUMSS main folder + filename'
               >>> where '%AMUMSS_PATH%' is internally replaced by the actual 'AMUMSS MAIN folder' path
                   Note: it does not need to point to 'ModScript\ModHelperScripts', just an example here
                   ex.: dofile([[%AMUMSS_PATH%\ModScript\ModHelperScripts\SayHello - child_4.lua]])
        
        * NOTE: for better error reporting, 
                it is STRONGLY suggested to locate (one or more) dofile() at the top of the script
                
    - GetEnvInfo()
        * An internal AMUMSS function (not to be used inside NMS_MOD_DEFINITION_CONTAINER table)
          Returns some environment information in a table with fields as shown below.
          You can use the returned information as you wish to decide what to do in the script.
          For example, if your script was to contain this code:

            print("## Environment Information")
            for k,v in pairs(GetEnvInfo()) do
              printf(" - %s = %s",k,v)
            end
            print("")
          Then log.lua will show (at the 'Running script internal code' phase):

            ## Environment Information
             - AMUMSSVer = 4.5.5.0W
             - NMSVerId = 123847
             - PublicExp = E
             - MBINCompilerVer = 4.71.0.1

NMS_MOD_DEFINITION_CONTAINER 
    - The Master Table (it defines the script table that will be processed by AMUMSS)  
    - always REQUIRED
    
  - TABLE or a TABLE of (1+)sub-table(s)  
    - members order is not important inside the table
    
    - MOST of the time, NMS_MOD_DEFINITION_CONTAINER is a TABLE and will produce one pak.
    
    - When it is a TABLE of 'one or more sub-tables', it is called a 'Multi-Container' script.
      It is like having one or more scripts in the same NMS_MOD_DEFINITION_CONTAINER
      and will be properly processed to create multiple paks.
      An example can be found in the >>> AMUMSS TEST_SCRIPTS collection: Test_Multi_Container.lua

        
    - Members of NMS_MOD_DEFINITION_CONTAINER are: 
        - ADD_FILES                 see ADD_FILES     - TABLE of (1+)sub-table(s) 
        - AMUMSS_SUPPRESS_MSG       OPTIONAL          - STRING
        - EXML_CREATE               OPTIONAL          - STRING or BOOLEAN    
        - GLOBAL_INTEGER_TO_FLOAT   OPTIONAL          - STRING  
        - LUA_AUTHOR                OPTIONAL          - STRING  
        - MOD_AUTHOR                OPTIONAL          - STRING  
        - MOD_BATCHNAME             OPTIONAL          - STRING  
        - MOD_CONTRIBUTORS          OPTIONAL          - STRING  
        - MOD_DESCRIPTION           OPTIONAL          - STRING  
        - MOD_FILENAME              REQUIRED          - STRING  
        - MOD_MAINTENANCE           OPTIONAL          - STRING  
        - MODIFICATIONS             see MODIFICATIONS - TABLE of (1+)sub-table(s)  
        - NMS_VERSION               OPTIONAL          - STRING or NUMBER

MOD_FILENAME 
    - member of NMS_MOD_DEFINITION_CONTAINER    
    - always REQUIRED  
    
    - a STRING, the name of the folder where the mod will reside in GAMEDATA/MODS 
        ex.:    ["MOD_FILENAME"]        = "someName",  
        (unless a combined mod is created, then the name may not be used)  
    - if MOD_FILENAME is not found, it will default to 'GENERIC' and a [WARNING] will be issued  
    - maximum name length is 122 characters

MOD_BATCHNAME 
    - member of NMS_MOD_DEFINITION_CONTAINER    

    - a STRING, the name of the folder where the mod will reside in GAMEDATA/MODS
        ex.:    ["MOD_BATCHNAME"]       = "someBatchName",  
    - if MOD_BATCHNAME is not found, it will default to AMUMSS name generation  
    - it supersedes the standard AMUMSS name when more than one .lua scripts are present and are combined 
    - maximum name length is 122 characters

MOD_AUTHOR - LUA_AUTHOR - MOD_MAINTENANCE 
    - members of NMS_MOD_DEFINITION_CONTAINER  
    - OPTIONAL  
    
    - a STRING
        ex.:    ["MOD_AUTHOR"]          = "ItIsMe",  
                ["LUA_AUTHOR"]          = "OrMe",  
                ["MOD_MAINTENANCE"]     = "unknown",  
    - Used for reference and in the *.pak_content.txt file of 'Combined' mods

MOD_CONTRIBUTORS - MOD_DESCRIPTION - NMS_VERSION 
    - members of NMS_MOD_DEFINITION_CONTAINER  
    - OPTIONAL  
    
    - a STRING (or a NUMBER, in the case of NMS_VERSION)
        ex.:    ["MOD_CONTRIBUTORS"]    = "anything goes",  
                ["MOD_DESCRIPTION"]     = "anything goes",  
                ["NMS_VERSION"]         = "1.77",  
    - Used for reference and in the *.pak_content.txt file of 'Combined' mods

GLOBAL_INTEGER_TO_FLOAT 
    - member of NMS_MOD_DEFINITION_CONTAINER    
    - OPTIONAL  
    
    - a STRING  
  
    - THIS IS ONLY USED TO SUPPRESS A MESSAGE
    
    ***** USE 'GLOBAL_INTEGER_TO_FLOAT' ONLY if you know that changing all INTEGERs to FLOAT is right  
        when the math operation results in a FLOAT  
      
    - Note: INTEGER_TO_FLOAT will supersede GLOBAL_INTEGER_TO_FLOAT if present  
  
    - [WARNING] even if you use this option to silence the AMUMSS WARNING/NOTICE's,  
        MBINCompiler may still refuse to compile the MXML when the underlying value is 'really' an INTEGER.  
  
    - '[WARNING] ORIGINAL(integer) and NEW(float) values are mismatched types'  
        You may see this WARNING in the REPORT.
        
        This WARNING only tells you that the script is changing an INTEGER "0" to a FLOAT "0.75"  

        If the MXML compiles correctly with MBINCompiler then it is alright,   
            otherwise it may be the case why MBINCompiler fails to compile the MXML.    
        >>> So it is an AID to you in finding a possible problem.  
      
    - can have one of these values: {nil, "", "FORCE", "PRESERVE"}  
        * default value is ""  
        * ["GLOBAL_INTEGER_TO_FLOAT"] = "FORCE", will change the INTEGER value to a FLOAT if necessary  
        * ["GLOBAL_INTEGER_TO_FLOAT"] = "PRESERVE", will keep the same type of value as before the operation  
            and hide: "[WARNING] ORIGINAL value below is INTEGER."   
            >> A FLOAT will still be a FLOAT  
            >> An INTEGER will still be an INTEGER (rounding up the value if necessary)

AMUMSS_SUPPRESS_MSG 
    - member of NMS_MOD_DEFINITION_CONTAINER    
    - OPTIONAL  
    - Value is case-insensitive  

    - a STRING, the name of the message to SUPPRESS   
        ex.:    ["AMUMSS_SUPPRESS_MSG"] = "SUPPRESS_FLOOR_DIV", -- one per line
                ["AMUMSS_SUPPRESS_MSG"] = "anotherOne",
                ["AMUMSS_SUPPRESS_MSG"] = "ThisOne, ThisTwo", -- or many per line
                ...
    - if found, it will SUPPRESS the message in the log.lua file AND in the REPORT.lua file  
    
    - multiple ["AMUMSS_SUPPRESS_MSG"] are allowed
    - values must be exactly the STRING shown below, not a variable with that value
    
    - current valid values are:  
        * ["AMUMSS_SUPPRESS_MSG"] = "SUPPRESS_FLOOR_DIV"
                  -- (notice regarding '//', floor division operator)   
        * ["AMUMSS_SUPPRESS_MSG"] = "MULTIPLE_STATEMENTS"
                  -- (notice regarding multiple_statements on same line)   
        * ["AMUMSS_SUPPRESS_MSG"] = "UNUSED_VARIABLE"
                  -- (notice regarding unused variables in script)   
            Note: allowing notices of 'unused' variables can be very helpful while developping a script
                  only SUPPRESS the message if you know what you are doing!!
        * ["AMUMSS_SUPPRESS_MSG"] = "UNDEFINED_VARIABLE"
                  -- (notice regarding undefined variables in script)   
            Note: allowing notices of 'undefined' variables can be very helpful while developping a script
                  only SUPPRESS the message if you know what you are doing!!
        * ["AMUMSS_SUPPRESS_MSG"] = "MIXED_TABLE"
                  -- (notice regarding presence of mixed_tables in script)
           Mixed tables are tables with indexed and keyvalue members.
            It is not good practice to have these, it can lead to difficult to read code and bugs
            Note: allowing notices of mixed tables can be very helpful while developping a script
                  ==> only SUPPRESS the message if you know what you are doing!!
        * ["AMUMSS_SUPPRESS_MSG"] = "NUMBERtoSTRING"
                  -- (notice regarding mismatched NUMBER to STRING types)

MODIFICATIONS 
    - member of NMS_MOD_DEFINITION_CONTAINER    

    - a TABLE of (1+)sub-table(s)    
    
    - can be used with or without ADD_FILES  
    - OPTIONAL when ADD_FILES is used, otherwise REQUIRED to create a mod
    - ["MODIFICATIONS"] = {}, is a valid use
    - MODIFICATIONS is processed AFTER ADD_FILES
    
    - member order is not important inside this table  
    
    - IF it is a TABLE of 'more than one sub-table', it is called a 'Multi-PAK' script.
      It is like having 2 or more scripts in the NMS_MOD_DEFINITION_CONTAINER
      and is properly processed.
      An example can be found in the >>> AMUMSS-ModLuaLearningCollection: Multi_PAK_Multi_MBIN_Example_Mod.lua

    - members of MODIFICATIONS are:  
        - MBIN_CHANGE_TABLE REQUIRED    - a TABLE or many tables  
        - PAK_FILE_SOURCE   OPTIONAL, NO LONGER REQUIRED (OBSOLETE - DEPRECATED)

PAK_FILE_SOURCE 
    - member of MODIFICATIONS    

    *** OBSOLETE - DEPRECATED ***
        
    - IS NO LONGER REQUIRED and will not be used  
    - (VERY OPTIONAL NOW) the NMS PAK "path and name" involved as a STRING  
    - always an original name from the NMS/PCBANKS folder  
    - the PAK_FILE_SOURCE "path and name" will be provided (and displayed) by AMUMSS

MBIN_CHANGE_TABLE 
    - member of MODIFICATIONS    

    - a TABLE of (1+)sub-table(s) 
    - alias is "MBIN_CT" (must be uppercase)  
  
    - member order is not important inside this table  
    - members of MBIN_CHANGE_TABLE are:  
        - COMMENT                       OPTIONAL  - STRING  
        - EXML_CREATE                   OPTIONAL  - STRING or BOOLEAN    
        - EXT_FUNC                      OPTIONAL  - TABLE of (1+)STRING
        - MBIN_FILE_SOURCE (MBIN_FS)    REQUIRED  - STRING or a TABLE or a (TABLE of (1+)sub-table(s))  
        - MBIN_FS_DISCARD               OPTIONAL  - STRING or BOOLEAN
        - MXML_CHANGE_TABLE (MXML_CT)   REQUIRED  - TABLE of (1+)sub-table(s) and STRINGs  
        - REGEXAFTER                    OPTIONAL  - TABLE of (1+)(two STRINGs and one OPTIONAL string)sub-table(s)  
        - REGEXBEFORE                   OPTIONAL  - TABLE of (1+)(two STRINGs and one OPTIONAL string)sub-table(s)

MBIN_FILE_SOURCE 
    - member of MBIN_CHANGE_TABLE    
    - REQUIRED  
    - alias is "MBIN_FS" (must be uppercase)  
    
    - NOTE: NMS path string are not restricted to MBIN files,
      but can be any text based types (.BIN, .CSV, .JSON, .TXT, .XML for example)
    
    - Alternate syntax #1: a NMS MBIN path STRING,  
          as in:
          [[METADATA\SIMULATION\SCENE\EXPERIENCESPAWNTABLE.MBIN]],  
        - used to work ONLY on this one file  
  
    - Alternate syntax #2: a TABLE of NMS MBIN path STRINGS, as in

SPECIAL_KEY_WORDS 
    - member of MXML_CHANGE_TABLE    
    - OPTIONAL  
    - alias is "SKW" (must be uppercase)  
     
    **** It is HIGHLY suggested to use TOOLS\MapFileTrees files to easily locate valid SPECIAL_KEY_WORDS ****
     
    - NOTE: if the supplied keywords are numbers, they are internally changed to STRING
    
    - A) a TABLE of (1+)(two STRING pairs) or B) a TABLE of ( SUB_TABLES of (1+)(two STRING pairs) ) 
        => KEYWORD STRINGs are case-insensitive
        => "valueX" can be the empty string ""
        => "", or {}, or {"",}, have no effect ==> all these mean: no SPECIAL_KEY_WORDS to search  
           (the whole file is used if nothing else selects a section)  
                
        ex.:    A) -- a TABLE of (1+)(two STRING pairs)
                   ["SPECIAL_KEY_WORDS"] = {"PropertyName1","value1","PropertyName2","value2",...},  
                   
                B) -- a TABLE of SUB_TABLES
                   -- where each SUB_TABLE is processed as if it was a TABLE of (1+)(two STRING pairs)
                   ["SPECIAL_KEY_WORDS"] = {
                     {"PropertyName1","value1","PropertyName2","value2",...},  
                     {"PropertyName1","value1","PropertyName2","value2",...},  
                     {"PropertyName1","value1","PropertyName2","value2",...},  
                     ...
                   }
                
                NOTE: when used as a TABLE of SUB_TABLES,
                      each sub-table is processed in turn as if it was like A: above
    
    - "Propertyname_1","value_1", ==> SPECIAL_KEY_WORDS pair #1  
      "Propertyname_2","value_2", ==> SPECIAL_KEY_WORDS pair #2
      ...
        that will be used (optionally with the PRECEDING_KEY_WORDS) to help define the SECTION(s)  
        we are looking for  
    
    - One or more pairs can be used of the form {"Propertyname_1","value_1","Propertyname_2","value_2",...},  
        => "Propertyname_1","value_1" defined a SECTION  
            then "Propertyname_2","value_2" defined a sub-SECTION of SECTION  
            and so on until the final sub-Section is found  
        => "Propertyname_X" and/or "value_X" can have the value "IGNORE"  
            if that helps selecting the right section (use with care!)  
        => "value_2" here (or the last of the "values" when multiple pairs are used) can be "IGNORE"  
            (useful in the case where NMS changes that value later)  
            see the script LearnMoreWords.lua as an example...  
    - If the line pointed to by the SPECIAL_KEY_WORDS pair(s) is found,  
        it will be used by LINE_OFFSET (if any present)  
  
    - ==> Both "Propertyname" AND "value" can be 'regular string expressions'
          (as defined by LUA 5.4 Patterns)
          REPLACE_TYPE is forced to "ALL".  SECTION_ACTIVE could override this behavior.
             Note: ^ (at the beginning) and $ (at the end)
                   are not required (and will be automatically removed if present)
            
          WARNING: In the MXML file, if "Propertyname" OR "value" natively includes
                   any one of the Lua 'magic' characters ^$()%.[]*+-?
                   You need to escape that character using %

    - WHAT ARE CONSIDERED SPECIAL_KEY_WORDS?
        =>> Have a look at the TOOLS\MapFileTrees folder for the file matching the MXML 
        * any line with a 'Property' AND a 'value'  
        * where the value is NOT ""  
        * lines with a value like a filename (???.MBIN or ???.xml for example)  
          are accepted as SPECIAL_KEY_WORDS  
            **** be warned that filenames like ???.MBIN could change more often  
                 and render your script obsolete!  
        * lines with a value like 'True', 'False' or a number are accepted as SPECIAL_KEY_WORDS  
            **** be warned that these types SHOULD be used with EXTREME CAUTION,  
                 HG could easily change the value!!!  
      
    - Works alone or with PRECEDING_KEY_WORDS (see OPTIONAL use below and MiningLaserSpeed.lua for example)  
    - If SPECIAL_KEY_WORDS are used, they are processed BEFORE the PRECEDING_KEY_WORDS  
        unless ["PRECEDING_FIRST"] = "TRUE"
    
    - See also Processing order to select section in AMUMSS

                  ["PRECEDING_KEY_WORDS"]   =  { -- where each SUB_TABLE is processed as if it was a TABLE of STRINGs
                    {"key1",},  
                    {"key1","key2","key3","key4",},  
                    {"key1","key3"},  
                    {"key3","key5",},  
                    ...  
                  },

                      each sub-table is processed in turn as if it was like B: above

             Note: ^ (at the beginning) and $ (at the end)
                   are not required (and will be automatically removed if present)
          
          WARNING: In the MXML file, if a "key" includes any one of the Lua 'magic' characters ^$()%.[]*+-?
                   You need to escape the character using %
    
    - With LEVEL 0 being the whole MXML file SECTION  
    - LEVEL key1, key2, ... defined SECTION and sub-SECTION heads (SECTIONs) in the MXML   
        file hierarchy (lines that end in [">] ) UNLESS used like in 'ALTERNATE USE' below  
        
    - Keys always refer to same LEVEL or sub-LEVEL keys   
    - Keys NEVER go back up the LEVEL chain
    - Skipping one or more LEVEL can work, specially if you want to specify many sections (see also REPLACE_TYPE)  
    
    - PRECEDING_KEY_WORDS works alone and with SPECIAL_KEY_WORDS  
        => If SPECIAL_KEY_WORDS are used, they are processed BEFORE the PRECEDING_KEY_WORDS  
        unless ["PRECEDING_FIRST"] = "TRUE"  
          
    - See also Processing order to select section in AMUMSS
    
    - In NORMAL use: (see also ALTERNATE USE)  
        With SPECIAL_KEY_WORDS, you use one or multiple PRECEDING_KEY_WORDS to further refine  
        the sub-section to look for inside the SECTION defined by the SPECIAL_KEY_WORDS.  
          
        If all these PRECEDING_KEY_WORDS are not found inside the SPECIAL_KEY_WORDS's SECTION,   
        the whole SPECIAL_KEY_WORDS's SECTION will be used (but your script has a problem and should be corrected)  
        
        Without any SPECIAL_KEY_WORDS, you also use one or multiple PRECEDING_KEY_WORDS to further refine  
        the sub-section to look for inside the whole file

        If GLOBAL EXML_CREATE is false then no EXML will be created

    - can have one of these values: {nil, "", "TRUE", "FALSE", true, false}  
            ex.: ["EXML_CREATE"] = "FALSE",  
    - "TRUE" instruct AMUMSS to attempt creating EXML files out of the NMS MXMLs

EXML_FLAGS 
    - member of MXML_CHANGE_TABLE    
    - OPTIONAL  
    
    - a STRING (case is not important)  
    - used to indicate that the flag should be added to the HOS of the current line of the generated EXML   
      (a HOS is a 'Head Of Section', the first line of a section in the MXML or EXML)
      
    - can have one of these values:  
        {nil, "", or Options listed below}  
        ex.:    ["EXML_FLAGS"]  = "OVERWRITE",      -- adds _overwrite="true"
            or  ["EXML_FLAGS"]  = "UPDATESECTION",  -- keeps original _id/_index
            or  ["EXML_FLAGS"]  = "ADDNEWSECTION",  -- removes existing _id/_index and do not add one
                  
    >>> Options:  
    - == "ADDNEWSECTION" : signals to remove and NOT use any [_index/_id] flag with the current HOS
                           This will tell the game to ADD the section at the end of the HOS    
    
    - == "UPDATESECTION" : signals to USE the current [_index/_id] flag with the HOS that you want to UPDATE 
    
    - == "OVERWRITE": signals to add the flag [_overwrite="true"] to the current HOS,
                      This will OVERWRITE the current section with new sections the script will provide
                      NOTE: this flag value forces the EXML section to contain
                            all of the original HOS section (including the changes)
                            making the EXML bigger, use only when really needed.

CUSTOM_ORDER 
    - member of MXML_CHANGE_TABLE    
    - OPTIONAL  
    - alias is "CO" (must be uppercase)  
    
    - a TABLE of STRINGS (the order of the STRINGs specifies processing order)
      
    NOTE 1: These are processed AFTER SKW/PKW section selection 
              See Processing order to select section(s) in AMUMSS
    NOTE 2: Each is processed only if the command is in use in the related MXML_CHANGE_TABLE
    NOTE 3: If the command is specified in the related MXML_CHANGE_TABLE
              but is not specified in CUSTOM_ORDER, it will be skipped

      (you have to ascertain the final section(s) selected are what you want)

SECTION_ACTIVE 
    - member of MXML_CHANGE_TABLE

                    <Property name="Race" value="GcAlienRace">

                    </Property>
                    ...
            
    - NOTE: SECTION_ACTIVE usually follows the _index value order in most cases, but not always

WHERE_IN_SECTION 
    - member of MXML_CHANGE_TABLE    
    - OPTIONAL  
    - alias is "WIS" (must be uppercase)  
    
    - a TABLE of (1+)(two STRINGs)sub-table(s)
        ex.:    ["WHERE_IN_SECTION"] =  
                {  
                    {"Property name/value1","WhereValue1",},  
                    {"Property name/value2","WhereValue2",},  
                    ...  
                },  
    - it is a table containing (1+)sub-table(s) of "two strings" describing:  
        a "Property name" or "Property value" we want to check the value of  
        and a "WhereValue" that will be compared to the original one in the MXML file  
      
    - "IGNORE" can be used in place of one or both strings  
    - an example use can be found in the script RewardTable_Test.lua
    
    - REPLACE_TYPE is forced to "ALL"
      one change, per SECTION per VCT item, found by the KEY_WORDS if they meet the conditions
      >>> UNLESS the script says REPLACE_TYPE = "ONCE"
          SECTION_ACTIVE could also override this behavior.
    
    - ==> Both "Property name/value" AND "WhereValue" can be 'regular string expressions'
          (as defined by LUA 5.4 Patterns)
             Note: ^ (at the beginning) and $ (at the end)
                   are not required (and will be automatically removed if present)
          
          WARNING: In the MXML file, if the "Property name/value" OR "WhereValue" includes
                   any one of the Lua 'magic' characters ^$()%.[]*+-?
                   You need to escape the character using %
    
    - by default, it acts like a logical 'OR' statement:   
                 >>> if any one pair is found then the section is retained
    - 'OR' (default):    
        For each SECTION specified by the KEY_WORDS:  
        A) IF none of the "Property name/value" with that "WhereValue" is found in the section   
            - then that SECTION is skipped/ignored  
        B) IF one or more "Property name/value" have that "WhereValue" in the section or a sub-section  
            - then that SECTION will be used by the script to update the MXML  
    
    - use ["WISEC_LOP"] = "AND" to make it act like a logical 'AND' statement:  
                 >>> if all pairs are found then the section is retained
    - 'AND':    
        For each SECTION specified by the KEY_WORDS:  
        A) IF all of the "Property name/value" with those "WhereValue" are found in the section   
            - then that SECTION will be used by the script to update the MXML  
        B) IF just one "Property name/value" does not have that "WhereValue" in the section   
            - then that SECTION is skipped/ignored  
    
    - use ["WISEC_LOP"] = "NOR" to make it act like a logical 'NOR' statement:  
                 >>> if ANY one of the conditions is TRUE then that section is NOT selected
    - 'NOR':    
        For each SECTION specified by the KEY_WORDS:  
        IF any of the "Property name/value" with those "WhereValue" are found in the section   
            - then that SECTION will NOT be used by the script to update the MXML  
    
    - WHERE_IN_SECTION is processed before WHERE_IN_SUBSECTION if also present  
        ==> See also Processing order to select section in AMUMSS

WISEC_LOP 
    - member of MXML_CHANGE_TABLE    
    - OPTIONAL  
     
    - a STRING  
    - DEFAULT value is the 'L'ogical 'OP'erator "OR" (one TRUE condition selects the section) 
    - used to change WHERE_IN_SECTION default behavior
    - can have one of these values: {nil, "", "OR", "AND", "NOR"}  
            ex.: ["WISEC_LOP"] = "AND",   
    - "AND" means that ALL the conditions must be TRUE for the section to be selected
        * the LAST pair of keywords defines the sub-section to be selected
    - "NOR" means that if ANY one of the conditions is TRUE then that section is NOT selected

          WARNING: In the MXML file, if the "Property name/value" OR "WhereValue" includes
                   any one of the Lua 'magic' characters ^$()%.[]*+-?
                   You need to escape the character using %
    
    - by default, it acts like a logical 'OR' statement:   
                 >>> if any one pair is found then the section is retained
    - 'OR' (default):    
        For each SECTION specified by the KEY_WORDS:  
      
        A) IF none of the "Property name/value" with that "WhereValue" are found in the section   
            - then that SECTION is skipped/ignored  
        B) IF one or more "Property name/value" have that "WhereValue" in the section   
            - that SECTION will be used by the script to update the MXML unless C) applies

            - then that SECTION is skipped/ignored  
        B) IF all "Property name/value" have that "WhereValue" in the section   
            - that SECTION will be used by the script to update the MXML unless C) applies 
        C) IF all "Property name/value" have that "WhereValue" in a SUB-SECTION of the section   
            - then that SUB-SECTION will be used by the script to update the MXML   
              instead of the original SECTION  
          
    - use ["WISUBSEC_LOP"] = "NOR" to make it act like a logical 'NOR' statement:  
                 >>> if ANY one of the conditions is TRUE then that section is NOT selected
    - 'NOR':    
        For each SECTION specified by the KEY_WORDS:  
        IF any of the "Property name/value" with those "WhereValue" are found in a sub-section   
            - then that SECTION will NOT be used by the script to update the MXML  
    
    - WHERE_IN_SUBSECTION is processed after WHERE_IN_SECTION if also present

SEC_SAVE_TO 
    - member of MXML_CHANGE_TABLE    
    - OPTIONAL  
    - alias: SEC_COPY
    
    - "" or a STRING  
        ex.:    ["SEC_SAVE_TO"] = "name_of_section",  
    - "name_of_section" is the name the modder will insert in the script  
        to refer to the SECTION content.  The SECTION content will be a STRING.  
    
    - It instructs AMUMSS to copy that section from the MXML for future use in the script  
    - The copied section is only in AMUMSS memory unless SEC_KEEP is used to also save it to disk 
    
        - WARNING: The sections saved in TOOLS\SavedSections are NOT deleted by AMUMSS.
                   That could lead to unforeseen use of an old saved section if your script
                   does not re-create it fresh for use by your script.
        
        - HOWEVER: The sections saved in TOOLS\SavedSections can be used by other scripts, 
                   if the scripts are aware of the name(s) given to the sections.
                   That can allow for multiple scripts to work together!
        
    - The section can come from a full MXML or be an already saved section (in the memory internal list)
    - Only the first section of multiple sections, returned by keywords + SECTION_ACTIVE/SECTION_UP/WIS/WISS, is saved  
    - Other members of MXML_CHANGE_TABLE can be used to change the section's values   
      BEFORE SAVING when using a VALUE_CHANGE_TABLE
      (Note that those changes also change the parent section: the full MXML or the current section in memory)
      
    - If the "name_of_section" already exist in memory, it is overwritten with the new content
    
    - A good usage example can be found in TEST_SCRIPTS\Test_DynamicMXML_CT_SEC_xyz.lua
      of the >>> AMUMSS Script Collection on github

MATH_OPERATION 
    - member of MXML_CHANGE_TABLE    
    - OPTIONAL  
    - alias is "MATH_OP" (must be uppercase)  
    
    NOTE: You can instead use VCT's INLINE math operations
    
    - nil or ""
    - or a STRING composed of "$"(OPTIONAL) + one of {+, -, *, /, //, %, ^}
    - or with SUFFIX (see below)
        
        ex.:    ["MATH_OPERATION"]  = "*",             -- NOT a SUFFIX type
            or  ["MATH_OPERATION"]  = "$-",            -- NOT a SUFFIX type
            or  ["MATH_OPERATION"]  = "*F:MaxAmount",  -- this is with SUFFIX
            or  ["MATH_OPERATION"]  = "!$*L:5",        -- this is with SUFFIX
  
    - "$" when used, swaps the order of the operands so that,  
         for example: (3 - 5 = -2, 'negative' 2) becomes (5 - 3 = 2, 'positive' 2)  
  
    MATH_OPERATION is applied 'after retrieving a LINE' pointed to by the KEYWORDS and   
                   the VALUE_CHANGE_TABLE (VCT) Property we are looking for  
                   (possibly redirected by LINE_OFFSET)

          Note: the value pointed to MUST be a numerical value (like "5.0" or 5), otherwise a value of 0 will be used  
              (so NOT a text string like [ALLOY1] here <Property name="Value" value="ALLOY1" />)  
          
    - "$"(OPTIONAL) + one of {+, -, *, /, //, %, ^} used alone will apply the math operation  
         between the VALUE at that LINE and the script VALUE_CHANGE_TABLE "newvalue".  
         Then use it as the mod "newvalue"  
  
    >>> [WARNING] {F:, FB:} is probably more robust to NMS changing things than {L:, LB:}  
                  With {L:, LB:}, a one line added/removed by NMS <<in between>> would prevent the expected change  

    - with SUFFIX == "!"(OPTIONAL) + "$"(OPTIONAL) + (one of {+, -, *, /, //, %, ^}) + (one of {F:, FB:})   
            + an endString ("IGNORE" or a Property Name STRING like [MaxAmount] 
            in this line: <Property name="MaxAmount" value="300" />)  
  
          F: == Fetch Forward (after) the current LINE for endString and get the value on that new line  
         FB: == Fetch Backward (before) the current LINE for endString and get the value on that new line  
  
         "!", when used, locks in the retrieved value to the first one found to be used in the calculation
         
         Now apply the math operation between this value and the script VCT "newvalue".  
         And then use it as the mod "newvalue".  
  
    - with SUFFIX == "!"(OPTIONAL) + "$"(OPTIONAL) + (one of {+, -, *, /, //, %, ^}) + (one of {L:, LB:}) + a NUMBER_OF_LINES  

          L: == Lookup Forward (after) the current LINE PLUS NUMBER_OF_LINES and get the value on that new line  
         LB: == Lookup Backward (before) the current LINE MINUS NUMBER_OF_LINES and get the value on that new line  
  
         NUMBER_OF_LINES should be calculated from the first NUMBER in the section (may not be the top of the section)  
         
         "!", when used, locks in the retrieved value to the first one found to be used in the calculation
         
         Now apply the math operation between this value and the script VCT "newvalue".  
         And then use it as the mod "newvalue".

    - OPTIONAL

            or  ["VALUE_MATCH"] = "False",  
            or  ["VALUE_MATCH"] = "TEXTURES/UI/LOADING/MIDDLEWAREPAIR.DDS",

           or  ["VALUE_MATCH"] = {"FOOTLOCKER", [[ABAND_CRATE]], "MEDTUBE",}, -- mixed literal and regular strings
           or  ["VALUE_MATCH"] = {"FOOTLOCKER", "{ABAND_CRATE}", "MEDTUBE",}, -- mixed literal and regular strings
      or a (TABLE defining a SUB_TABLE of two STRINGs and/or NUMBERs)) to define a RANGE

    - Multiple values are treated as (string1 OR string2 Or string3 OR ...) for triggering a match  
    - 'literal string value' and 'regular string expression' can be used in the same VALUE_MATCH declaration
    
    - Can be used with or without SKW / PKW to trigger the VCT replacement
    
    - a 'literal string value' or NUMBER from the MXML file that matches exactly the "original value" we want to change  
        like if we wanted to change only values when the 'original value'
        is "5" or "0.2345678" or "Snow" or "False" or any other string  
    
        * see 'CreatureSizeAndSpawnRateIncrease.lua' and 'MoreScreenFilters.lua' as examples  
    
    - or, a TABLE defining a SUB_TABLE of ONLY two STRINGs and/or NUMBERs (a RANGE of values):
        ex.:    ["VALUE_MATCH"] = { {"5","9"} },   -- a range of 5 to 9
                ["VALUE_MATCH"] = { {5,9} },       -- same range from 5 to 9
                ["VALUE_MATCH"] = { {"9",5} },     -- same range from 5 to 9
                ["VALUE_MATCH"] = { {[[9]],5} },   -- same range from 5 to 9
                ["VALUE_MATCH"] = { {5.2,9.7} },   -- a range from 5.2 to 9.7

        that will match the "original value" (that is a REAL STRING, not a NUMBER) we want to change  
        (DO NOT USE 'regular string expression' with NUMBERS, use VALUE_MATCH_OPTIONS)  
        ex.:    ["VALUE_MATCH"] = "{REPAIR%.DDS$}",  
             --> notice the escape character '%.' making the '.' a real 'dot', not the 'all characters' pattern  
                 and the $ to anchor the search to the end of the string  
                    matches: "TEXTURES/UI/LOADING/MIDDLEWAREPAIR.DDS"  
             does not match: "TEXTURES/UI/LOADING/MIDDLEWARE.DDS"

        * to target 'empty string values' use ["VALUE_MATCH"] = "{^$}", with VALUE_MATCH_OPTIONS = "=", or "~=",  
    
    - see 'Test_VALUE_MATCH Patterns.lua' as an example

VALUE_CHANGE_TABLE 
    - member of MXML_CHANGE_TABLE    
    - OPTIONAL  
    - alias is "VCT" (must be uppercase)  
    
    - a TABLE of (1+)sub-table(s) of (two STRINGs and two "OPTIONAL STRINGs")  
        ex.:  
            ["VALUE_CHANGE_TABLE"]  = {  
                    {"Property name/value1", "newvalue1",},
                    {"Property name/value2", "newvalue2",},
                    
                    -- saves current value of "Property name/value3" to optional "NamedValue"
                    {"Property name/value3", "newvalue3", "NamedValue",},  
                    
                    -- retrieves optional value "NamedValue" and use it instead of "newvalue4" value
                    {"Property name/value4", "newvalue4", "{:}NamedValue",}, 

                    -- execute your script function anyFunctionName()
                    -- saves current value of "Property name/value3" to optional "NamedValue"
                    {"Property name/value5", "FUNC_TEST()" ,"NamedValue",},  
                    
                    -- execute your script function anyFunctionName()
                      -- retrieves value "NamedValue" and use it instead of "newvalue4" value
                    {"Property name/value6", "FUNC_TEST()", "{:}NamedValue",}, 
                    
                    -- execute your script function anyFunctionName()
                      -- passes "" for "NamedValue" and a string as argument to FUNC_TEST()
                    {"Property name/value7", "FUNC_TEST()", "", "FuncArg"}, 
                    
                    -- execute your script function anyFunctionName()
                      -- passes "" for "NamedValue" and a TABLE of arguments to FUNC_TEST()
                    {"Property name/value8", "FUNC_TEST()", "", TableOfFuncArg}, 
                    ...  
            },  
    
    - in other words, a table containing one or more "two or three string" tables describing:  
        - 1st STRING: the "Property name=" OR "Property value=" we want to change the 'currentvalue' of  
        - 2nd STRING: a "newvalue" that will replace the original one in the MXML file OR a "anyFunctionName()" 
        - OPTIONAL 3rd STRING: see "NamedValue"
        - OPTIONAL 4th STRING: arguments to the 2nd STRING "anyFunctionName()"
        
    - 1st and 2nd STRING can have a value of "IGNORE" in some cases (like when we use LINE_OFFSET)  
        - syntax examples:  {"Bonus","IGNORE",}, or  {"IGNORE","IGNORE",}, or  {"IGNORE","100",},  
            * {"Bonus","IGNORE",}, makes AMUMSS goto and SKIP the line with "Property name/value" == "Bonus",  
            * {"IGNORE","IGNORE",}, makes AMUMSS SKIP the next line,  
                doing NO exchange at all and continuing processing the next "Property name/value"  
            * {"IGNORE","100",}, makes AMUMSS change the line "value" to "100" regardless of the "Property"  
        
    - to update a group of numerical 'Property value=' using (for example) a ["MATH_OPERATION"] = "*"  
        and ["VALUE_CHANGE_TABLE"] = {{"IGNORE","1.5"},},  
        to multiply << each >> value by 1.5 without the need for ["LINE_OFFSET"]  
        
    - For 1st STRING: "Property name/value":
          ==> please see "Property name/value" for more general info 
          ==> case-insensitive
          ==> "Property name/value" can be a 'regular string expression' (as defined by LUA 5.4 Patterns)  
                 Note: ^ (at the beginning) and $ (at the end)
                       are not required (and will be automatically removed if present)
              
              WARNING: In the MXML file, if the "Property name/value" includes
                       any one of the Lua 'magic' characters ^$()%.[]*+-?
                       You need to escape the character using %

            A 'regular string expression' is enclosed in curly brackets {...},  
            and will match "Property name/value" we are looking for  
          ==> If all "Property name/value" are the same and not 'IGNORE'   
            then AMUMSS will adjust the next line automatically (including LINE_OFFSET, if used)   
            in order to continue replacing down the section/file
        
            [WARNING] For ex.: "Bonus" here will trigger AMUMSS automatic line_adjustement  
                            ["VALUE_CHANGE_TABLE"]  = {  
                                    {"Bonus","100",},  
                                    {"Bonus","50",},  
                                    {"Cost","25",},  -- bad idea, AMUMSS will complain!
                            },
                      
                      This could lead to unreliable replacements!  
                      Do not mix/use different "Property name/values""  
                      Please, in this case, split into two MXML_CHANGE_TABLE sub-tables instead
                          using the same KEYWORDS and other commands in both except the VALUE_CHANGE_TABLE

    - For 2nd STRING: newvalues: 
          ==> Case A: a 'newvalue' of the form "String1{:}String2" will concatenate the three strings and
            replace the 'ORIGINAL_VALUE' represented by {:} with 'SomethingORIGINAL_VALUESomethingelse'
            when "Something" is String1 and "Somethingelse" is String2
            In other words, the 'ORIGINAL_VALUE' represented by {:} is prefixed by the left side of {:}
            and suffixed by the right side of {:}.
            
            One or both sides of {:} can be an empty string
            (both sides empty is equivalent to keeping the 'ORIGINAL_VALUE' intact)
            
            String1 and / or String2 can be variable names in the script.
            The newvalue would then be written as String1.."{:}"..String2 if both are script variables
            
          ==> Or if first character of 'newvalue' is '@', an INLINE MATH_OP is triggered
            and a 'newvalue' of the form "@optNum1MATH_OPoptNum2" will replace 
            the 'Original Value' of "Property name/value" with the result of the MATH_OP
                
                Note: space characters are allowed between tokens (for easier readability)
                >>> @: always 1st character of string, triggers evaluation of INLINE MATH_OP
                >>> optNum1: required when MATH_OP is of type SUFFIX
                >>> MATH_OP: one of the MATH_OPERATION, see how rules apply
                >>> optNum2: required when MATH_OP is one of {+, -, *, /, //, %, ^} (not of type SUFFIX)

            For ex.: VCT = {
                             {"MaxAmount", "@*5" },   -- 'MaxAmount' new value = current value * 5
                             {"MaxAmount", "@ - 5" }, --      "      new value = current value - 5
                             {"MaxAmount", "@+5" },   --      "      new value = current value + 5
                             ...
                             {"MinAmount", "@6 * F:MaxAmount" },   -- this is a MATH_OPERATION with SUFFIX
                             {"MinAmount", "@ -6 * F:MaxAmount" }, -- negative number used
                             {"MinAmount", "@!$20/L:5" }, -- SUFFIX: Note: the '5' in 'L:5' is the NUMBER_OF_LINES
                             {"MinAmount", "@1*F:MaxAmount" }, -- Replace MinAmount with value of 'F'orward (MaxAmount * 1)
                             ...
                           },
          ==> Case B: if the 'newvalue' is of the form ' anyFunctionName() ' AND that function exist in your script:
            then that script's function is called with 4 arguments: 
                           1) "Property name/value" name as STRING
                           2) the current value of that "Property name/value" as STRING
                           3) nil or the retrieved "NamedValue", if it exist / was used as the 3rd parameter
                           4) nil, a STRING, a NUMBER, a BOOLEAN or a TableOfArguments
                                  as an 'ExtraArgToFunc' argument to 'anyFunctionName()'
                           
            The script's function(s) can do whatever you want with these arguments
            BUT must return at least 'one' value that will be used as the "newvalue"
            (all other returned values are discarded)
              >>> If the returned value is the string "IGNORE", then the replacement for this VCT entry
                  will be skipped
            
            For instance, a VCT script function can add to the script new MXML_CT sections dynamically
               (as long as the new MXML_CT sections are added after the current one, 
                 a good usage example can be found in TEST_SCRIPTS\Test_DynamicMXML_CT_SEC_xyz.lua
                 of the >>> AMUMSS Script Collection on github)
            
            You can have multiple script functions to do different processing.
            
            For ex.: VCT = {  -- FUNC_TEST(), for example, must be one of your script function 
                    -- 1st     2nd            3rd                        4th argument
                    { [[ID]], "FUNC_TEST()", [nil | "" | "NamedValue"], [nil | STRING | NUMBER | BOOLEAN | TABLE] },
                 },

                In your script, you would have, for example, function FUNC_TEST:
                    
                    function FUNC_TEST(property,currentValue,NamedValue,ExtraArgToFunc)
                      NamedValue = NamedValue or aScriptVar or ""
                      -- print("SCRIPT: FUNC_TEST = ["..tostring(currentValue).."] ["..tostring(NamedValue).."]")
                      -- the script can do anything here, even calling other script functions
                      -- ExtraArgToFunc is an argument (or a table of) that you defined in your script
                      local newValue = property.."+"..currentValue.."+"..NamedValue
                      return newValue
                    end
                    
            NOTE: the script FUNC_TEST() must be a global function of the script
                          (NOT a "local function xyz()...end")
        
    - See also EXT_FUNC for more advanced processing of script functions, not tied to VCT
        
    - For OPTIONAL 3rd STRING "NamedValue"
      ==> It represents a name you give, as an internal variable,  
        that will record the current value of "Property name/value", for future use in the script(s),
        in a global script variable
      ==> You can retrieve that value using the syntax "{:}NamedValue" as the 3rd STRING.
      ==> When trying to retrieve a previously saved value: 
         - The retrieve value is use instead of "newvalue"
           EXCEPT when used with anyFunctionName() (the function decides to use it or not)
         - If not found, the value will default to the 2nd STRING "newvalue"

        >>> script 'Test_GUIF_VCT.lua' is a good example to better understand what follows...

                * If 'Wait' parameter is nil or omitted,

Meaning of "Property name/value" in this document 

    In this document, "Property name/value" means the name of a "Property name="   
        OR the value of a "Property value=" in the MXML files.  
    
    "value" here does NOT refer to the "value=" part   
        of lines like <Property name="ThisPropertyNAME" value="ThisPropertyValue" />  
    
    For example, if a fictional MXML contains:
        ...
        <Property name="Name" value="TEMPLATE_NAME" />   -- Case 1
        <Property name="ActiveLodDistances">             -- Case 2
          <Property value="TkLODDistances.xml">          -- Case 2
            <Property name="Distances">                  -- Case 2
              <Property value="0" />                     -- Case 3
              <Property value="10" />                    -- Case 3
              <Property value="40" />                    -- Case 3
            </Property>                    -- never used
          </Property>                      -- never used
          <Property name="List" />                       -- Case 4
          ...
        </Property>                        -- never used
        ...
            
    Case 1:          <Property name="Name" value="TEMPLATE_NAME" />
        ->  "Property name" is named "Name"       and has a "value=" of "TEMPLATE_NAME"
        ->  The left-side of VALUE_CHANGE_TABLE would be "Name", the Property to change
            and the "newvalue" would replace "TEMPLATE_NAME"  
        ->  This type of "Property name/value" can be used with SPECIAL_KEY_WORDS
        
    Case 2:          <Property value="GcStatsBonus.xml">
                 or  <Property value="TkLODDistances.xml">
                 or  <Property name="Distances">
        ->  These have "Property name/value" associated with them
            like "GcStatsBonus.xml", "TkLODDistances.xml" and "Distances"  
            but they do not have a "value=" associated with them
        ->  This type of "Property name/value" cannot be used with VALUE_CHANGE_TABLE  
            They can be used with PRECEDING_KEY_WORDS and VALUE_MATCH  
        
    Case 3:          <Property value="0" />
                 or  <Property value="10">
                 or  <Property value="40">
        ->  Have no "Property name/value"             but have "value=" of "0", "10" or "40"   
        ->  Having no "Property name", we substitute "IGNORE" for the left-side   
            and the right-side "newvalue" would replace current value "0", "10" or "40" in a VALUE_CHANGE_TABLE  
            depending which line is current based on the script commands
        ->  VALUE_MATCH can use them

    Case 4:          <Property name="List" />
        ->  This cannot not be used in a VALUE_CHANGE_TABLE

            },

Usage and Types of "Seed" in scripts 

    There are two types of "Seed" in MXML files:  "GcSeed" and "List<long>"
    
    A) "Seed" that are member of "GcSeed" must represent a "ulong" (which is a "System.UInt64" in C# .net).
       These "Seed" cannot be negative, the range is 0 through 18446744073709551615 decimal
       (0x0 to 0xffffffffffffffff in hex, 16 hex char long).
    
    B) Negative seeds exist.  They can be found in "ListOfValues" and are defined as "long".
       Thus these can be negative to cover the full range of a "long"
       (-9,223,372,036,854,775,808 to 9,223,372,036,854,775,807).
    
    ==> Notice that seeds are always decimal numbers, a string, in the MXML/EXML files.
        No "Seed" ever contains the hex digits: "ABCDEF" nor "0x".

    How to determine if a seed is "ulong" or "long"?
        * If the "Seed" is just one value in a section, it is a "ulong" (and is never negative)
        * If the "Seed" is part of a "ListOfValues" ("List<long>" in this case),
          it is a "long" (and can be negative)

    For example, "GenerationSeed" in DEFAULTSAVEDATA.MXML is a "GcSeed", a "ulong"
    and the string representation of the decimal number of the "Seed".
    In other words, "GenerationSeed" value is a decimal as a string in MXML/EXML files.

    IF you search for Property Name="Fallback Seeds" and "Preset Fallback Seeds" in MXML files,
    you will see that they are "ListOfValues" and being "long", they can have positive or negative values.
    
    In a script: if you have, for example, a variable like this:
       local MySeed = 0x0x99767CB16FF97BA9 -- 11058163036584508329 decimal
       
       "string.format("%u",MySeed)" will transform it into the proper string for a "GcSeed" type
       "string.format("%d",MySeed)" will transform it into the proper string for a "long" type in a "ListOfValues"

        HOES are closed properties with no content (body) within them, commonly found in SCENE files.

              ...
              <Property name="Children" />  
            </Property>  
          </Property>
          ...

       NOTE: Possible HOES are now reported by TOOLS\MapFileTrees as "[H.."

    >>> Method 1) THE PREFERRED METHOD  Example:


            ["MXML_CHANGE_TABLE"] =
            {
                {
                    SKW = {"Name","pointLight1",}, -- command that select the right section
                    PKW = {"PossibleOtherKeyWord(s)","Children",}, -- PKW last entry that points to the HOES we want to expand

    [[
              <Property value="TkSceneNodeData.xml">
                <Property name="Name" value="RR_SuspensionBotJNT" />
                <Property name="NameHash" value="1590240059" />
                ...
                <Property name="Children" />
              </Property>
    ]],
                },
            },
    


        NOTE: This method does not work when SKW and PRECEDING_FIRST = "TRUE" are used together
        NOTE: This method does not required the use of ADD_OPTION

            Keywords select the section where the HOES 'property' is.
            Here the HOES is: 'Children' as in the LINE <Property name="Children" />
            AND PKW LAST ENTRY points to it.

            auto-replace <Property name="Children" /> with the new empty section:
                <Property name="Children">
                </Property>
            
            The ADD string (or a named variable that contains a string) will be the body
                An alternate to ADD is to use SEC_ADD_NAMED

                Notice that the ADD string is ONLY the body of the new section, without the enclosing
                    <Property name="Children">
                    </Property>

                },
            },
    


        This is what happens:
            Keywords select the section where the VCT 'property' is located
            Here the HOES is: 'Children' as in a LINE like (<Property name="Children" />)
                and VCT uses "IGNORE" (because there is no 'value=')
            With ["ADD_OPTION"]  = "REPLACEatLINE",
                triggers the ADD (or a named variable that contains a long string)
                in place of the LINE and removes the LINE in one go

                    </Property>

A LocTable.txt file is in the script folder... 
    Using a simple text file named LocTable.txt in the script folder allows AMUMSS to create a LocTable.MXML
    in the mod folder when processing the script.
    
    Multiple LocTable.txt files will be combined into one LocTable.MXML when creating a COMBINE mod.
    
    The format of the LocTable.txt file is very simple, for example, this LocTable.txt:

    =ARRIVE_IN
    EN =We'll be there in
    FR =Encore

    =PLANET_NAME
    EN=This planet is called :
    FR=Planète :

    =UI_MOVE_TECH_TIP
    EN =<IMG>SELECT<> Choose SLOT
     to move technology

    =NOTIFY_TAKEOFF
    EN=

    "=ARRIVE_IN" specifies the "Id" value
    The following lines are the values for the languages (one or many)
    
    The language value can be written as NMS writes them:
        &lt;IMG&gt;SELECT&lt;&gt; Choose SLOT&#xA; to move technology
    
    Or, in a more natural way:
        <IMG>SELECT<> Choose SLOT
     to move technology
    
    Either way will result in the same value.
    
    It will produce a LocTable.MXML, in the CreatedMODS sub-folder for the mod, like this:

    <?xml version="1.0" encoding="utf-8"?>

Handling of LocTable files(.MXML/.txt) 
    ==> Handling of LocTable(.MXML/.txt) files goes like this:
        1) If a LocTable.txt or a LocTable.MXML is in the script folder,
           it will be used to create the final LocTable.MXML.
           If both are present, they are merged
        2) If a LocTable.txt and/or a LocTable.MXML is created by the script, they are merged with 1)
        3) If one or more LANGUAGE files are modified by the script,
           they are turned into a merged LocTable.txt with 1) and 2)
           and used to create the final LocTable.MXML.
        4) Multiple scripts in a COMBINE contribute to 3).
        5) The final LocTable.MXML is used as the language file
           in CreatedMods folder and in the GAMEDATA/MODS mod sub-folder.
        6) The LocTable.txt used to create the final LocTable.MXML is also copied 
           to the mod/CreatedMods folders with the scripts used to create the mod.
        7) The TOOLS/MODDER_HELPER folder is then populated, as usual, with all the files 

    ==> If a LocTable.MXML is in GlobalMEFTI, it will be copied into all mod folders created.
        A better practice is to ONLY include the LocTable(.MXML or .txt) file in the sub-folder for that script.
    ==> There is no need to put a LocTable.MXML file in the MEFTI sub-folder of a script.

        * When MBIN files are used, if 2 mods modify the SAME MBIN file, the last mod to load THAT file wins
          (overwrites the MBIN file loaded before) (see also 'NMS Load Order' above).  

          Which means that some (or all) of the files from an earlier loaded mod are used 
          and some (or all) of the files from a later loaded mod are also used
          when they are not the same exact files by name (.MBIN, .DDS, ...).

          BUT if any are the same MBIN files, the last mod to load that or those particular file(s)
          always 'wins the contest' and overwrites these individual MBIN files to be used by NMS.

        * When EXML files are used, they will conflict only if the EXML files change the same value.
          You can control which mod wins by changing the load order.  Or, if the EXML files change multiple
          of the same values, by combining the mods OR by hand picking the values to your liking.

What AMUMSS will do... 
    While following the 'Load Order', AMUMSS will do...
    
    - When only paks are in 'ModScript':
        * each pak is unpacked/decompiled and saved in its own folder in 'TOOLS\UNPACKED_DECOMPILED_PAKs'
    
    - When only ONE pak is in 'ModScript':
        * the pak is unpacked/decompiled and saved in its own folder in 'TOOLS\UNPACKED_DECOMPILED_PAKs'
        * If a .lua script is found in the PAK, you are asked if you want to rebuild a MOD from
          that script...
    
    - When only ONE or MORE .lua scripts are in 'ModScript':
        * If a 'combined' pak is requested, all the scripts will be used to create the pak mod
        * If an 'individual' mod is choosen instead, each script will create it owns pak mod
        
    - When ONE or MORE .lua scripts with ONE or MORE paks are in 'ModScript'...
        * the scripts will look into each pak to try locating the required MBINs and, if found, 
          use them.  Otherwise, NMS MBINs will be used
        * you can create Patch mods with this
        
            ========================= WARNING ========================

    Having more than one pak in ModScript will NOT combine both paks if they modify the same MBIN file,
    only the last MBIN loaded will combine with the script(s)
          
    - AMUMSS can handle correctly multiple paks in ModScript
      but be aware that only the last same mbin file loaded will be the one used by the script(s)
        
            ================== VERY IMPORTANT WARNING ================

    Using an 'older' pak (a pak that is NOT updated to the 'current' NMS MBIN file content)  
    could result in a not functional pak that could crash NMS.

    - Since AMUMSS will fetch the MBIN (called for by the script(s)) from the 'older' pak, 
      if that MBIN is NOT a modded 'current' version, the resulting modded MBIN may not be
      compatible with NMS
        
    - Note that AMUMSS cannot correct the faulty MBIN when it is an older version because it cannot
      know if the changes made in the 'older' pak to the MBIN were intentional (by the modder)
      or due to NMS upgrading that MBIN

    - When only MBINs are in 'ModScript':
        * The .MBINs are passed to the appropriate MBINCompiler.exe to decompile them to .MXML
        
        * Drop all MBINs in AMUMSS Modscript folder by themselves (no scripts in ModScript).
          Execute BUILDMOD.bat or BUILDMOD_AUTO.bat and they will get decompiled by the right MBINCompiler.
          MBIN files do not even need to be in a proper NMS path.  Just the files by itself works.
          Decompiled MBINs will be in AMUMSS\ModScript\EXMLFILES_PAK.

        * The .EXML versions are only the exact .MXML versions with the extension changed.
          Not to be use directly but can be manually edited to a proper EXML if one wishes... 
        
    - When EXMLs are in 'ModScript':
        * NOTE: This feature has not been fully tested in all situation and could have side-effects
        * With scripts: if the EXMLs are in proper NMS / script folders as indicated by the script,  
          the .EXMLs are used in place of NMS / decompiled MBINs  
          These ModScript EXMLs have priority over NMS pak ones!!!
        * Without scripts: If the EXMLs are in proper NMS folders
          a valid GENERIC mod (that you should rename) will be created from those EXML files
        
    - If any files are in folder 'ModScript\GlobalMEFTI',  
        depending on your OPTIONS, you will be asked if you want to include them in the final PAK   
        All created paks will contain these files if you answer 'Y'
        
        These files can be viewed as global files you want all your paks to contain
        
    - If any files are in the sub-folder 'MEFTI' of a custom script folder,
        they will be automatically included in the final PAK.

        A custom script folder is a sub-folder of ModScript that includes ALL parts 
        of your mod (.lua script and where extra files are in its own 'MEFTI' folder)
        Thus making it easy to create a full package to distribute   
        
        if a "MEFTI" folder is present in a sub-folder, it's content will be included   
        for the scripts in that sub-folder and end up in the mod   
        
        However, if you said 'Y' to create a combine mod and any ModScript sub-folders have "MEFTI" folders,   
        then these "MEFTI" folders will also contribute to the final combine mod
        
        see also BASIC ModScript folder structure

    - Where do MBINs/MXMLs come from?
        Note: .MBIN are files found inside the game .pak files in PCBANKS folder
                and we access them by unpacking the .pak file using HGPAGTool (either .py or .exe version)
                or NMSPE->Unpack
        
        * If a .MBIN required by a script is already in 'MODBUILDER\MOD', it is used
        
        * ElseIf some .pak(s) is/are present in 'Modscript':
            First look for the .MBIN in all the paks (last pak loaded with the .MBIN wins)
            and then in NMS PCBANKS if not found

        * Else (no .pak is present in 'ModScript'):
            Locate the NMS PCBANKS pak containing the .MBIN and extract it to 'MODBUILDER\MOD'
            
        * Each .MBIN is passed to the appropriate MBINCompiler.exe to decompile it to an .MXML

    - Note: If some lua scripts reference (individually or collectively) ALL .MBINs in a pak in 'ModScript',
            then all the .MBINs 'of the pak' will end up in the final mod
          
            Do not delete that original pak 'forever' because the changes 
            in those .MBINs may not have been 're-created' completely in the provided lua script(s),
            you may need to keep it, as a reference, to re-create the mod after a future NMS update.

About sub-folders in your 'GAMEDATA\MODS' folder 
    - Anything in a sub-folder of 'GAMEDATA\MODS' is ignored by the game
      if it does not contain valid NMS paths, even if a sub-sub-folder is present

About 'disabling' mods in your 'GAMEDATA\MODS' folder 
    - Disabling mods (sub-folders) in your 'GAMEDATA\MODS' folder can be done by one of:
        * Editing the No Man's Sky\Binaries\SETTINGS\GCMODSETTINGS.MXML file and
          changing "Enabled" (and "EnabledVR", if applicable) to "false"
        * Removing the mod sub-folder file from 'GAMEDATA\MODS' (cut and paste elsewhere)
        * Making a new sub-folder in 'GAMEDATA\MODS' and moving the mod sub-folder into it.
          Anything in a sub-folder of 'GAMEDATA\MODS' is ignored by the game
          if it does not contain valid NMS paths
